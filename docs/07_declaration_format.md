# 07. 최종 산출물: 세관 신고 양식 (기초재고반입)

## 한 줄 요약
기초재고 마이그레이션의 결과물은 "신규 시스템 재고 테이블"만이 아니라 **관세청에 보내는 물품반입검사신청서(Header/Detail)** 형태다.
고객이 말한 "저렇게 뽑으면 된다"는, 계산한 기초재고를 **보세구역·장치장별로 묶어 신고구분 Z(기초재고반입) / Y(미인도물품재고반입)** 신고서로 만들라는 뜻.

## 보세구역과 장치장 (고객 설명, 2026-11-20 HS 세관재고 기준)
보세구역 1개에 장치장 여러 개 (1:N).

| 보세구역 (신고지점 wh_code) | 연결된 장치장 |
|---|---|
| 01022006 신세계면세점 본점 | 01022006 본점 · 04077090 제2 통합물류센터 · 04077137 은산 통합물류창고 |
| 04021040 인천공항 제1터미널점(DF4) | 04021040 T1 · 04077090 제2 통합물류센터 · 04077137 은산 통합물류창고 |
| 04021041 인천공항 제2터미널점(DF4) | 04021041 T2 · 04077090 제2 통합물류센터 · 04077137 은산 통합물류창고 |

**→ 이전 조회 결과와 맞아떨어짐**: 통합물류는 별도 점이 아니라 **각 점(보세구역)의 재고가 놓인 장치장**.
그래서 기초재고는 **보세구역 3개 × 장치장 3개 = 최대 9개 칸**으로 나뉨.

| | 자기 장치장 (본점 / T1 / T2) | 통합물류 장치장 (04077090, 04077137) |
|---|---|---|
| 상품 | HS세관재고 (− 미인도, 본점만) | 계산재고 = 수불 + 교환권 − H재반입 − 미인도 |
| GWP | 본점: 계산재고 / T1·T2: 수불재고 | 계산재고 |
| 미인도 | 본점: Y 신고 (교환권번호별) / T1·T2: 없음 | Y 신고 (교환권번호별) |

(해석 — 고객 확인 필요. 특히 "통합물류 = 계산재고"가 각 보세구역의 통물 장치장분을 말하는지)

## 이걸로 바뀐 판단
1. **Q5 (통합물류 단위)** → 사실상 답이 나옴: 보세구역별 통물 장치장. 남은 건 **코너(961/965 등) ↔ 장치장(04077090/04077137) 매핑**.
2. **Q2 (미인도 "−")** → 정상(Z)에서 빼고, 같은 수량을 **교환권번호별로 Y 신고**하는 것으로 보임. → 미인도는 빌 단위 상세를 끝까지 유지해야 함 (`sql/05` 가 SRC_BILL_NO 를 보관하는 이유).
3. **환급코드 분리** → 신고 Detail 의 **물품구분(T/W/H/D)** 으로 나누는 것으로 보임. 세관재고는 WM0121L.CSTM_ITEM_CLS_CD(MA071), 수불은 REFU_CLS_CD(GO407) 를 이 값으로 매핑.
4. **수량만이 아니라 상품정보·판매가가 필요** → 상품마스터 테이블 확인 필요.
5. 양식의 형식(datetime, numeric, int)으로 보면 **신규 시스템 DB 는 Oracle 이 아닐 수 있음** (SQL Server 등) → 적재 방법 확인.

## SQL
- `sql/06` 최종 집계: 결과를 (보세구역, 장치장, 상품/GWP, 정상/미인도, 물품구분, 상품, 교환권번호) 단위로 변경
- `sql/08_declaration_output.sql`: MIG_BASE_STOC → 신고 Header/Detail 스테이징(MIG_DECL_H/D) 생성 (9,999 품목 분할, 신고번호 채번, 검증)
- `sql/09_insert_target.sql`: MIG_DECL_H/D → **SR_ItemCarryIn_H / SR_ItemCarryIn_D INSERT**. 같은 DB·DB Link 면 INSERT…SELECT, 다른 DB 면 INSERT 문을 텍스트로 생성

```
수불·세관재고·매출 → MIG_STOC_COMP(구성요소) → MIG_BASE_STOC(기초재고) → MIG_DECL_H/D(신고 스테이징) → SR_ItemCarryIn_H/D
```
